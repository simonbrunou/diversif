# Deploy

What a production deploy does, how to check one from a workstation, and where to read a production environment value. The migration runbook, rollback and the Sentry checks after a deploy live in [`DEPLOY.md`](../../DEPLOY.md).

## What a merge to `main` sets off

- **Trigger**: every push to `main` on Forgejo (a PR merge) that changes a file outside `*.md` and `docs/` starts a Coolify deploy through a webhook. The app's Coolify watch paths (`!*.md`, `!**/*.md`, `!docs/**`, set 2026-10-28) skip a push that changes only those files: no image is built and production keeps running the previous commit. The deploy does not wait for CI, so the CI run on the new `main` head is a separate check.
- **Build**: Coolify builds with Railpack's node provider, set in `railpack.json`. It installs the Bun version pinned there, installs the dependencies with `HUSKY=0`, and runs the `build` script from `package.json` (the provider's default build step). The image then starts `bun build/index.js` with `NODE_ENV=production`, `PROTOCOL_HEADER` and `HOST_HEADER` (`deploy` in `railpack.json`).
- **Source maps**: with `SENTRY_AUTH_TOKEN` set at build time, the `diversif:sentry-upload-after-adapter` plugin in `vite.config.ts` creates the Sentry release once the adapter has run, uploads the source maps of `./build` and deletes every `.map` file, so the image never serves them.
- **Release name**: Coolify sets `SOURCE_COMMIT` to the commit it builds. Unless `SENTRY_RELEASE` overrides it, `vite.config.ts` uses it as the Sentry release and as SvelteKit's `version.name`, so `/_app/version.json` reports the SHA that is live.
- **Start**: the new container runs the migrations and the food-catalog seed on boot (see `DEPLOY.md`), and Coolify swaps it in once it is healthy.
- **Duration**: about 4 minutes from the merge until `/_app/version.json` shows the new SHA.

## Check a deploy

After a merge, run `scripts/smoke-prod.sh <sha>` with the SHA of the newest `main` commit that changes a deployed file: `git fetch origin && git log -1 --first-parent --format=%H origin/main -- . ':!*.md' ':!docs'`. After a code merge that is the new `main` head; after a merge that changes only `*.md` or `docs/` files it is an older commit, already live, since the watch paths skipped the deploy. Run it in one foreground Bash call with `timeout: 600000`. It polls `/_app/version.json` until that SHA is live, for 540 s at most (`SMOKE_WAIT` in seconds overrides it). Then it runs public HTTP checks only. The whole run, retries included, ends at most `SMOKE_WAIT` + 50 s after it starts (`SMOKE_CHECK_TIME` in seconds overrides the 50), so 590 s by default, inside that call. No request or `git fetch` outlives that deadline, and a check that has not started by then is not sent: it prints `FAIL <check> not run: the time budget ran out` and counts as failed. Run the script again after such a FAIL: the SHA is live by then, so the second run's wait ends at once. It fails at once on an argument that is not a SHA, on a SHA that `origin/main` does not contain after a `git fetch origin`, and when the file you run is a copy rather than a checkout's own `scripts/smoke-prod.sh`: a copy in `/tmp` can't tell whether a newer live commit contains the SHA, so its wait would time out after a later merge. When that fetch fails, or is still running 1 s before the deadline, which cuts it off, it skips the `origin/main` check and waits. A newer `main` commit that contains the SHA counts as live, so a second merge during the wait does not fail the run. Its last line reads `smoke-prod: N of N checks passed on https://diversif.app`.

It exits 1 when a check fails or `/_app/version.json` never reports a version. When an older commit still serves after the wait, it prints a `PENDING` line, skips the checks and exits 3: the deploy is still running, or it failed. Run homelab-stacks `scripts/coolify-deploy-status.sh` with the diversif app uuid from its header and the SHA. Its exit 0 or 3 means run `smoke-prod.sh` again. On any other exit, its last line says what went wrong.

A request sent during the container swap can get no answer, or only part of one. So when curl exits with an error (a timeout, a refused or reset connection, an empty reply, a body cut short), the script tries that check again, up to 3 more times, 5 s apart. Each retry prints a `RETRY` line with the check, the attempt number and the curl error. A check that passes on a retry counts as one pass. A full answer with a wrong status, content type, header or body fails at once, a 5xx included. Once one check has used up its retries, the script treats the host as down, and later checks whose curl call fails get no retry. No retry starts when its 5 s sleep would end at or after the run deadline: the check then fails with the curl error it got. The wait on `/_app/version.json` keeps its own 15 s polling and does not retry this way. It ends by `SMOKE_WAIT`: its last sleep is cut short so that its last poll starts 1 s before then, and that poll's request gets the 1 s left.

What it expects:

- `/`, `/guide` and `/en` answer 200 `text/html`.
- `/` carries a `Content-Security-Policy` with `default-src 'self'`, `Strict-Transport-Security` (sent only when `NODE_ENV=production`, see `src/hooks.server.ts`) and `X-Frame-Options: DENY`.
- `/healthz` answers 200 with `"ok":true` and `"db":"ok"` in its JSON (it also carries `uptimeMs`).
- `/_app/env.js` answers 200 JavaScript. It holds the runtime public env values: the prerendered `/offline` page imports it, and the service worker keeps a copy in its `app-env` cache.
- `/service-worker.js` answers 200 JavaScript: `src/lib/components/ReloadPrompt.svelte` registers it.
- `/sw.js` answers 404 on purpose. It was the old vite-pwa worker, gone since the SvelteKit 3 migration.
- `/offline` (prerendered) answers 200 HTML. It comes back with no `Content-Type` header today, which the script accepts.

To check the service worker by hand, open the site in a browser (the Playwright MCP tools work). `ReloadPrompt.svelte` registers the worker after the page's `load` event, so hydration alone proves nothing: once `await navigator.serviceWorker.ready` resolves, the worker at `/service-worker.js` is active and its install has filled the `workbox-precache-v2-…` cache. It also warms the `app-env` cache, but only as best effort, so that cache can exist and still be empty.

To check a change by hand once `smoke-prod.sh` has passed, first read the build SHA in each page you fetch, since every page's HTML holds its build's `version: "<sha>"`. The old container can still answer after `/_app/version.json` reports the new SHA. After #533's merge, the first POST sent right after a passing `smoke-prod.sh` run came from the previous commit's container, and a retry a little later came from the new one. When a page holds the old SHA, send the request again until it holds the new one. To fetch the page that a visitor without JavaScript gets back after a form submit, POST with `Accept: text/html` and `Origin: https://diversif.app`. Without the `Accept` header, SvelteKit answers with the action's JSON. Without `Origin`, it answers 403 `Cross-site POST form submissions are forbidden`.

The deployment queue, the build log, the container's health and the source-map upload are prod internals. Check them from the private homelab repo (homelab-stacks `scripts/coolify-deploy-status.sh`), not from here.

A production environment value, such as `BODY_SIZE_LIMIT`, is a prod internal too. The homelab-stacks runbook `docs/operations/runbooks/ct-103-diversif.md` has the command, under "Read one environment value". Print only that variable: the environment also holds secrets.
