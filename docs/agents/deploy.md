# Deploy

What a production deploy does, how to check one from a workstation, and where to read a production environment value. The migration runbook, rollback and the Sentry checks after a deploy live in [`DEPLOY.md`](../../DEPLOY.md).

## What a merge to `main` sets off

- **Trigger**: every push to `main` on Forgejo (a PR merge) that changes a file outside `*.md` and `docs/` starts a Coolify deploy through a webhook. The app's Coolify watch paths (`!*.md`, `!**/*.md`, `!docs/**`, set 2026-10-28) skip a push that changes only those files: no image is built and production keeps running the previous commit. CI skips the E2E job and the three build jobs (bundle budget, backup restore check, Docker build) of a PR that changes only paths on the skip list of `scripts/e2e-needed.sh`. That list is wider than the watch paths: it also holds agent tooling (`.claude/` and the rule-hook scripts with their tests), so a merge that changes only agent tooling skips E2E on its PR and still deploys. A path added to the watch paths goes on the skip list too. The deploy does not wait for CI, so the CI run on the new `main` head is a separate check.
- **Build**: Coolify builds the `Dockerfile` at the repo root (build pack `dockerfile` since deployment 3439 on 2026-11-19, #788), the image CI's `Docker build (smoke test)` job builds and boots. The `builder` stage installs every dependency with `HUSKY=0` and runs `bun run build`. The runtime stage starts again from the pinned `oven/bun` image and runs `apt-get upgrade` (next bullet). It adds the user `diversif` (uid 1001). It copies `build/`, the `node_modules` of the `prod-deps` stage, `package.json`, `drizzle/` and three operator scripts. It starts `bun build/index.js` as `diversif`. It sets `NODE_ENV=production`, `PORT=3000`, `HOST`, `PROTOCOL_HEADER`, `HOST_HEADER`, `WEBAUTHN_RP_ID` and `DATABASE_PATH`. The Coolify app also holds `NODE_ENV`, `PROTOCOL_HEADER`, `HOST_HEADER` and `DATABASE_PATH`, with the same values, and adds `ADDRESS_HEADER`, `BODY_SIZE_LIMIT`, `RETENTION_INACTIVE_DAYS`, the legal variables and the Sentry ones. Its exposed port is 3000. Coolify inserts an `ARG` line for each build-time variable after every `FROM` of the file it builds, so `SENTRY_AUTH_TOKEN` and `SOURCE_COMMIT` reach `bun run build`. The data volume `/app/data` belongs to uid 1001 (`chown -R 1001:1001` on 2026-11-19), since the server cannot write the database otherwise.
- **Debian fixes**: the runtime stage runs `apt-get update` and `apt-get upgrade` in one `RUN`, so the image takes the Debian security fixes published after the pinned base image was built (#788: `apt` and `libapt-pkg7.0` for CVE-2026-109518, `zlib1g` for CVE-2026-85091). On 2026-11-19, a Trivy scan (`--severity HIGH,CRITICAL --ignore-unfixed`) of a build without that `RUN` listed both CVEs, and the build with it listed no finding. In a local build or CI's Docker build job, BuildKit reuses that layer from its cache until a line above it or the `RUN` changes, a new base digest from Renovate included. To take a Debian fix sooner, set `ARG APT_REFRESH` to today's date. Coolify's builds rerun the layer on each deploy of a new commit: the `ARG SOURCE_COMMIT` it inserts after the last `FROM` holds the commit, and a build argument whose value changes reruns every `RUN` after it. A redeploy of the same commit can reuse the cached layer.
- **Dev dependencies stay out of the image**: the runtime stage takes `/app/node_modules` from the `prod-deps` stage, which runs `bun install --frozen-lockfile --production --ignore-scripts`, so the image ships the production dependencies and what Bun installs with them (#529). That set still holds 8 of the 39 devDependencies, each named by another package in the set (checked in the image on 2026-11-19). `@sentry/sveltekit` has `@sveltejs/kit` as a peer, whose own peers are `@sveltejs/vite-plugin-svelte`, `svelte` and `vite`. The other four are optional peers, which Bun installs from `bun.lock`: `eslint` of `@inlang/paraglide-js`, `typescript` of `@sveltejs/kit` and `valibot`, `yaml` and `@types/node` of `vite`. Dev tooling that no production package names, such as `playwright`, `@playwright/test`, `fallow`, `knip`, `svelte-check` and `drizzle-kit`, is gone. The operator scripts that `README.md` and `DEPLOY.md` run in the container import only Bun or Node builtins (`scripts/cleanup.ts`, `scripts/list-stale-users.ts`, `scripts/verify-backup-restore.ts`), or ship as one bundled file (`build/scripts/export-user.js`, see `build:scripts`), so they need no devDependency. Keep a new one to the same rule.
- **Source maps**: with `SENTRY_AUTH_TOKEN` set at build time, `sentrySvelteKit()` in `vite.config.ts` creates the Sentry release and its deploy marker once the adapter has run, uploads the source maps of `./build` and deletes every `.map` file, also when the upload fails, so the image holds none. A successful upload logs one `[sentry-vite-plugin] Info: Successfully uploaded source maps to Sentry` line in the build log. `nodeAdapter()` in `scripts/node-adapter.ts` keeps the client maps out of adapter-node's asset table, so a `.map` URL answers what it answers in a build that wrote no maps: 404 `Not found` under `/_app/`, and the app's HTML 404 page at the root, such as `/service-worker.js.map` (#722).
- **Release name**: Coolify sets `SOURCE_COMMIT` to the commit it builds, at build time too, since the app's `include_source_commit_in_build` setting is on. Unless `SENTRY_RELEASE` overrides it, `vite.config.ts` uses it as the Sentry release and as SvelteKit's `version.name`, so `/_app/version.json` reports the SHA that is live.
- **Start**: the new container runs the migrations and the food-catalog seed on boot (see `DEPLOY.md`), and Coolify swaps it in once it is healthy. Coolify's own health check is off on the app (`health_check_enabled: false`): it probes with `curl` or `wget` inside the container, and the image has neither (#370). Coolify then waits on the image's `HEALTHCHECK`, a `bun -e` fetch of `/healthz` every 30 s after a 20 s start period, and the deploy log shows `Using the custom healthcheck from the Dockerfile.`, then `New container is healthy.` before `Rolling update completed.`
- **Duration**: about 4 minutes from the merge until `/_app/version.json` shows the new SHA, measured on the build pack production used before 2026-11-19. Deployment 3439, the first build from the `Dockerfile`, took 165 s from its queue entry to `Rolling update completed.`

## Check a deploy

After a merge, run `scripts/smoke-prod.sh <sha>` with the SHA of the newest `main` commit that changes a deployed file: `git fetch origin && git log -1 --first-parent --format=%H origin/main -- . ':!*.md' ':!docs'`. After a code merge that is the new `main` head; after a merge that changes only `*.md` or `docs/` files it is an older commit, already live, since the watch paths skipped the deploy. Run it in one foreground Bash call with `timeout: 600000`. It polls `/_app/version.json` until that SHA is live, for 540 s at most (`SMOKE_WAIT` in seconds overrides it). Then it runs public HTTP checks only. The whole run, retries included, ends at most `SMOKE_WAIT` + 50 s after it starts (`SMOKE_CHECK_TIME` in seconds overrides the 50), so 590 s by default, inside that call. No request or `git fetch` outlives that deadline, and a check that has not started by then is not sent: it prints `FAIL <check> not run: the time budget ran out` and counts as failed. Run the script again after such a FAIL: the SHA is live by then, so the second run's wait ends at once. It fails at once on an argument that is not a SHA, on a SHA that `origin/main` does not contain after a `git fetch origin`, and when the file you run is a copy rather than a checkout's own `scripts/smoke-prod.sh`: a copy in `/tmp` can't tell whether a newer live commit contains the SHA, so its wait would time out after a later merge. When that fetch fails, or is still running 1 s before the deadline, which cuts it off, it skips the `origin/main` check and waits. A newer `main` commit that contains the SHA counts as live, so a second merge during the wait does not fail the run. Its last line reads `smoke-prod: N of N checks passed on https://diversif.app`.

It exits 1 when a check fails or `/_app/version.json` never reports a version. When an older commit still serves after the wait, it prints a `PENDING` line, skips the checks and exits 3: the deploy is still running, or it failed. Run homelab-stacks `scripts/coolify-deploy-status.sh` with the diversif app uuid from its header and the SHA. Its exit 0 or 3 means run `smoke-prod.sh` again. On any other exit, its last line says what went wrong.

A request sent during the container swap can get no answer, or only part of one. So when curl exits with an error (a timeout, a refused or reset connection, an empty reply, a body cut short), the script tries that check again, up to 3 more times, 5 s apart. Each retry prints a `RETRY` line with the check, the attempt number and the curl error. A check that passes on a retry counts as one pass. A full answer with a wrong status, content type, header or body fails at once, a 5xx included. Once one check has used up its retries, the script treats the host as down, and later checks whose curl call fails get no retry. No retry starts when its 5 s sleep would end at or after the run deadline: the check then fails with the curl error it got. The wait on `/_app/version.json` keeps its own 15 s polling and does not retry this way. It ends by `SMOKE_WAIT`: its last sleep is cut short so that its last poll starts 1 s before then, and that poll's request gets the 1 s left.

The old container can still answer after `/_app/version.json` reports the new SHA (#533, below), so a check could pass on the previous build. So, given a SHA, the script also reads the build SHA of each HTML page it fetches (`/`, `/guide`, `/en`, `/offline`): the `version: "<sha>"` of SvelteKit's inline boot script. A page passes only when that SHA is the one given, or a newer `main` commit that contains it, the rule the wait uses. A page that holds an older SHA is fetched again 5 s later, and each new fetch prints a `REFETCH` line with the page, the SHA it held and the seconds left in the SHA budget. That budget is 60 s, shared by all pages, from the moment the wait saw the SHA live, about twice the overlap measured below. When the SHA goes live less than 60 s before the run deadline, the budget ends at that deadline. Once the budget is spent, the page fails with `FAIL <page> holds build <old sha> after the 60 s SHA budget, expected <sha> or a newer main commit`. When the deadline cut the budget, that line gives the shorter budget instead of 60 s. A page whose HTML holds no `version: "…"` fails at once. A page that passes after new fetches counts as one pass, and the header checks on `/` read the answer that held the accepted SHA. Each new fetch goes through the no-answer retry above, and a full answer with another status fails at once. Without a SHA the script reads no build SHA, and runs 11 checks instead of 12.

The #542 thread measured that overlap on 2026-11-12, on the deploy of `ca65783` (#752, Coolify deployment 3210), which replaced `51ce412`. All times below are Paris time. A probe loop ran from 21:44:48, 5 minutes before `/_app/version.json` changed, until 31 s after the last old answer. Each round it read the build SHA of `/` and of `/_app/version.json`, each with a new `curl` process, then slept 1 s, so a round took about 1.2 s. `/_app/version.json` gave the first answer from the new build at 21:49:50. `/` gave the last answer from the old build at 21:50:19. Between the two, both containers answered, mostly in turn. The probe's rounds put the window at 29 to 31 s. The new container had started at 21:49:43, and the deployment finished at 21:50:20 (created at 21:44:44, 336 s), about 37 s after that start. Triage had read about 32 s from container start to old-container removal in the logs of deployments 2716 to 2718. The maintainer's decision on #542 was to raise the budget if the measured window exceeded 30 s. The first new and the last old answer came 29 s apart, so the 60 s budget stays. The probe's 1.2 s rounds allow a window of up to 31 s, and 60 s is still about twice that. The `smoke-prod.sh` run during that deploy fetched `/`, `/guide` and `/en` again once each, and passed 12 of 12. Its last `REFETCH` line showed 49 s of the budget left. If a later run fails a page `after the 60 s SHA budget`, measure again the same way and raise `SHA_TIME` in the script.

What it expects:

- `/`, `/guide` and `/en` answer 200 `text/html`. Given a SHA, they and `/offline` hold that build's SHA or a newer one that contains it.
- `/` carries a `Content-Security-Policy` with `default-src 'self'`, `Strict-Transport-Security` (sent only when `NODE_ENV=production`, see `src/hooks.server.ts`) and `X-Frame-Options: DENY`.
- `/healthz` answers 200 with `"ok":true` and `"db":"ok"` in its JSON (it also carries `uptimeMs`).
- `/_app/env.js` answers 200 JavaScript. It holds the runtime public env values: the prerendered `/offline` page imports it, and the service worker keeps a copy in its `app-env` cache.
- `/service-worker.js` answers 200 JavaScript: `src/lib/components/ReloadPrompt.svelte` registers it.
- `/sw.js` answers 404 on purpose. It was the old vite-pwa worker, gone since the SvelteKit 3 migration.
- `/offline` (prerendered) answers 200 HTML. It comes back with no `Content-Type` header today, which the script accepts.

To check the service worker by hand, open the site in a browser (the Playwright MCP tools work). `ReloadPrompt.svelte` registers the worker after the page's `load` event, so hydration alone proves nothing: once `await navigator.serviceWorker.ready` resolves, the worker at `/service-worker.js` is active and its install has filled the `workbox-precache-v2-…` cache. It also warms the `app-env` cache, but only as best effort, so that cache can exist and still be empty.

To check a change by hand once `smoke-prod.sh` has passed, first read the build SHA in each page you fetch, since every page's HTML holds its build's `version: "<sha>"`. The script reads it only in its own four pages, and the old container can still answer a later request after `/_app/version.json` reports the new SHA. After #533's merge, the first POST sent right after a passing `smoke-prod.sh` run came from the previous commit's container, and a retry a little later came from the new one. When a page holds the old SHA, send the request again until it holds the new one. To fetch the page that a visitor without JavaScript gets back after a form submit, POST with `Accept: text/html` and `Origin: https://diversif.app`. Without the `Accept` header, SvelteKit answers with the action's JSON. Without `Origin`, it answers 403 `Cross-site POST form submissions are forbidden`.

The deployment queue, the build log, the container's health and the source-map upload are prod internals. Check them from the private homelab repo (homelab-stacks `scripts/coolify-deploy-status.sh`), not from here.

A production environment value, such as `BODY_SIZE_LIMIT`, is a prod internal too. The homelab-stacks runbook `docs/operations/runbooks/ct-103-diversif.md` has the command, under "Read one environment value". Print only that variable: the environment also holds secrets.
