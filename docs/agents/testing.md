# Tests

How to run, write and triage this repo's tests. Commands live in `package.json`; this file holds what the scripts don't say.

## Running

- **`bun run test`**, with `bun run test <path>` for a focused run. It wraps `scripts/bun-test.ts`: paraglide compile, SvelteKit sync, then one `bun --conditions=browser test` process per file, so `mock.module` overrides stay inside their file. Bare `bun test` drops the browser condition, and every `@testing-library/svelte` component test fails with `` `mount(...)` is not available on the server ``: the command is wrong, not your change. A direct `bun --conditions=browser test <file>` skips the paraglide compile, so in a fresh worktree it fails with `Cannot find module '#lib/paraglide/runtime.js'` from `bunfig.preload.ts`: run `bun run paraglide` once (every `bun run test` does it first).
- **Coverage**: the 100% line gate runs only under `bun run test:coverage`, which is what CI runs.
- **Typecheck**: `bun run check` type-checks the shared helpers in `src/test/` along with the app, and every TypeScript file under `scripts/`, its tests included, through `tsconfig.scripts.json`. It checks every TypeScript file in `e2e/` and `playwright.config.ts` through `tsconfig.e2e.json`. A spec that calls a helper it never imports then fails `bun run check`, which the pre-push hook and CI's `Lint + typecheck` job run (#363). Through `tsconfig.tooling.json`, it checks the lint rules under `eslint-rules/`, their tests included, and the root `*.preload.ts` files that `bunfig.toml` loads before every test file (#658). The rules stay JavaScript typed with JSDoc: type a rule object as `RuleModule` from `eslint-rules/ast.js`, which gives each visitor the nodes the parser builds (typescript-eslint's `TSESTree`, svelte-eslint-parser's `AST`), where ESLint's own `Rule.RuleModule` knows only plain ESTree nodes. It checks the unit and component tests under `src/` like the app code (#554). Declare a route's load as `export const load = (async (event) => { … }) satisfies PageServerLoad;` (or `LayoutServerLoad`), not `export const load: PageServerLoad = …`: the annotation types its result as `Record<string, any>`, so every field a test reads is `any`. In a test, read a load's result through `loadData(await load(event))` from `src/test/route.ts`, which fails the test when the load returned nothing, and pass the event `makeRouteEvent(…)` builds: its type is the event of the handler it is passed to.
- **Dependency audit**: `scripts/audit-deps.sh` runs both `bun audit --audit-level=high` scopes of the CI job `Dependency vulnerability audit` with the job's own commands, or one scope with `production` or `all`. Run it when a brief asks for both audit scopes "as the CI job runs them".
- **Worktrees run through the dev shell.** `bun` is on PATH only inside the flake's dev shell, and a new worktree is not `direnv allow`ed, so prefix commands with `nix develop -c`. A fresh worktree needs `nix develop -c bun install --frozen-lockfile` first. Run `git push` that way too: the husky pre-push hook first fetches `origin/main` and refuses a push that conflicts with it (`scripts/check-base-conflict.sh`), then runs `bun run lint`, `bun run check` and CI's Fallow audit against `origin/main` (about 80 s). That audit fails a function above cognitive complexity 15 or cyclomatic 20 (`.fallowrc.json`, which raises the cognitive limit for Svelte `<template>` markup only). While you write a script or a long function, run `FALLOW_AUDIT_BASE=origin/main nix develop -c node_modules/.bin/fallow audit` (after one `bun run check` in the worktree, which generates the files it reads): it takes about a second and names each function over the limit, where a refused push costs a refactor and a second push (#663, #714, #365). Outside the dev shell, where `bun` is missing, the hook runs itself again inside `nix develop .`, so a push without the prefix runs the same checks. On a conflict, merge the base it names into the branch as « Merge authority » in `AGENTS.md` says, then push again. On a branch stacked on another, push with `FALLOW_AUDIT_BASE=origin/<parent>`, which both checks then use as the base. It does not run the bundle budget: before you push a change that adds client code, run `bun run check:budget` (a full build, about 30 s). The pre-commit hook runs `npx lint-staged` under node and needs only `node_modules`.
- **The dev shell's Bun may lag the pinned one.** CI's `bun-version` inputs, `railpack.json` (production) and the `Dockerfile` pin one Bun, which Renovate's bun group moves and `scripts/check-bun-pins.sh` checks in the `Lint + typecheck` job. The dev shell takes `pkgs.bun` from nixpkgs through `flake.lock`, which Renovate does not update, so it runs whatever Bun nixpkgs shipped when the lock was last bumped: 1.4.2 on 2026-10-27, while the pins read 1.4.4. `scripts/check-bun-pins.sh` prints the pinned version and warns when the shell runs another. A result can depend on the version: Bun 1.4.4's coverage counts a default-parameter line that 1.4.2's does not (#528). To get CI's result locally, run the command through `scripts/pinned-bun.sh`: `nix develop -c scripts/pinned-bun.sh bun run test:coverage`. It puts the pinned Bun first on PATH, after downloading it once into `~/.cache/bun-pinned/<version>` and checking it against the release's `SHASUMS256.txt`. Write `bun.lock` through it too: `nix develop -c scripts/pinned-bun.sh bun install`. Bun 1.4.2's `bun install` without `--frozen-lockfile` drops the `libc` field from 50 native packages' entries, even when `package.json` did not change, and CI's `bun install --frozen-lockfile` on 1.4.4 accepts that lockfile, so no check catches it (#658).
- **A passing test's time: unset Bun's agent variables.** Bun prints only failing tests and the summary when `CLAUDECODE`, `AGENT=1` or `REPL_ID` is set. Claude Code's shell sets `CLAUDECODE`, and every process it starts inherits it (`codex sandbox -- env` lists it), so a run from Claude Code, or from a Codex sandbox it started, shows no `(pass)` line and no per-test time. CI's dump of a failed file shows them. To see them, run the file as `nix develop -c scripts/pinned-bun.sh env -u CLAUDECODE -u AGENT -u REPL_ID bun --conditions=browser test <file>`. `bun run test` prints only a progress line for a passing file.
- **E2E from a worktree: give the run a free port.** Outside CI the Playwright `webServer` reuses any server already listening on its port, and the default 4173 is also where another worktree's E2E run or `bun run preview` serves its own build. Take 4000 plus the issue number (4452 for #452), check that `ss -ltn 'sport = :4452'` shows no listener, then run `nix develop -c env PORT=4452 bun run test:e2e e2e/offline.spec.ts`. The database file is already per worktree (`./e2e-test.db`, gitignored), and `test:e2e` resets it at the start of every run, so leave it in place afterwards.
- **Start an E2E job only when no other one runs or waits.** Until #478 gives E2E its own runner, two Playwright jobs on the shared runner can time each other out. Opening or reopening a PR starts an E2E job, and so do a push to an open PR's branch, a merge to `main` (its push run has one) and a rerun of the E2E job or of a whole run. A push to a branch with no PR starts none. The E2E job of a PR whose branch changes only Markdown files and `docs/` runs no Playwright test: CI's `changes` job runs `scripts/e2e-needed.sh`, and the E2E job reads `blocked` while `changes` runs, then `skipped`. A push to `main` runs it whatever the change. Before each of them, run `scripts/wait-e2e-slot.sh` in one foreground shell call with a 10-minute timeout (Claude Code: `timeout: 600000`). Chain the command that starts the job with `&&`, as in `scripts/wait-e2e-slot.sh && nix develop -c git push`. A pipe through `tail` turns its busy exit 3 into success. When the checked-out branch changes only those files, is pushed and has never had a PR into `main`, it exits 0 at once and claims nothing, since opening that PR starts no Playwright test. Merging such a PR still waits, since the push to `main` runs E2E. Otherwise the script leaves out the run of your branch's pushed head (`origin/<current branch>`), which the next push cancels, and waits up to 7 minutes while another run's `End-to-end tests (Playwright)` job is `waiting` or `running`, printing each busy run. When the command you chain works on a branch other than the checked-out one, pass the script's `<own sha>` argument (in full, or its first 7 characters or more), or the checked-out branch's run goes uncounted (#631). On 2026-11-02, a session opened a PR for its checked-out branch, and that PR's E2E job queued. 11 s later, from the same worktree, it chained a call with no argument before `fj pr -R origin create --head <another branch>`. The call left out the first PR's run as its own and cleared at once. Pass:
  - to open or reopen a PR for another branch, that branch's pushed head, as in `scripts/wait-e2e-slot.sh "$(git rev-parse origin/<branch>)" && fj pr -R origin create --head <branch> ...`. `origin/<branch>` holds the head that a push or a `git fetch origin` from any worktree of this clone last saw, so fetch first when another clone or host pushed the branch;
  - to merge a PR from a checkout on another branch, the PR's head SHA, which leaves out the same run as a call from the PR's own worktree;
  - to rerun another branch's run, or one of its jobs, that run's `commit_sha`.

  A push to the checked-out branch, or a rerun of its own run, takes no argument. Each poll also queues your worktree in a file the sessions on this host share, and the sessions take the slot in the order they joined (#615). When the slot clears, only the waiter that joined first gets exit 0. It claims the slot in that file for 4 minutes, time for its run to show up on the forge, and leaves the queue. While that claim is fresh, the others read busy, and a new call from the holder (after a failed pre-push hook, say) goes first again once its forge check reads clear. A busy poll prints one `ahead in the queue: <worktree>, waiting since <time>` line for each waiter before yours. A call that ends on exit 3 keeps your place for your next call. A waiter that has not polled for 2 minutes drops out and joins at the back when it calls again, and exit 2 drops it at once. Exit 0 means clear and your turn, 3 still busy or behind another waiter (run it again at once), 2 a missing or refused token or a wrong call. To rerun one job, take its id from `GET $API/actions/runs/<id>/jobs`, where `<id>` is the run's `id`, not its index (« Read the failing job's log first »). An `actions/tasks` entry's `id` is a task id, not a job id (« Triaging a red run »). Then call `POST $API/actions/jobs/<job id>/rerun`. `$API` and the token come from `docs/agents/issue-tracker.md`. When the E2E job you wait for comes from a session the queue does not see, on another host or from a push made without the script, message that session and take turns, each telling the other when its E2E job ends.

- **Review a branch before you open its PR.** A push to a branch with no PR starts no E2E job, but each fix pushed to an open PR starts one, and that push has to wait for the slot again. So push the branch, run its review and every re-check, and open the PR once they leave nothing to fix. On 2026-11-06, #686 opened before its re-check, and the re-check's two wording fixes then waited about 42 minutes for the slot: first behind the E2E run that the PR's opening had started, then behind another thread's.

- **Rules for review sub-agents.** A reviewer's brief quotes the author's `bun run test:coverage` summary and coverage lines (`N files | P pass | F fail | S skip | Ts`, then `Coverage (merged lines …): a/b lines — p%`). The reviewer takes them as the suite's result, and CI runs the suite again before the merge. The reviewer runs only the test files that cover the diff: those the diff adds or changes, and those of the source files it changes (`nix develop -c bun run test <file>…`). A reviewer told to check the author's claims checks them against those lines and the diff, within the same budget. A reviewer that can write also runs the mutation check of « A mutation check: commit first » in `docs/agents/testing.md`, on the one test file that covers the reverted change. A second full suite takes about 6 minutes of the CPU that the host's agent threads share, and repeats what the author's lines already show. On 2026-11-08, #577's Spec reviewer re-ran it: 333 s of its 537 s review. Before its first write, a reviewer makes a directory of its own for its files (notes, probes, logs), outside the checkout under review. It runs `mktemp -d -p <scratch> review-XXXX`, where `<scratch>` is the scratch dir its brief or its session names, or `mktemp -d` when neither names one outside that checkout. It reads the author's files where they are, and puts a mutation-check worktree where « A mutation check: commit first » says. Reviewers that write at the top of one scratch dir write over each other's files: two sutom#197 reviewers had to redo their probes (nix#79, 2026-11-02), and on 2026-11-11 #710's first re-check overwrote the `issue710.txt` that its Spec reviewer had written at the top of the author's scratch dir.

- **A mutation check: commit first.** The `git checkout -- <file>` or `git restore <file>` that undoes a mutation also drops your unstaged edits to that file. `git restore -s HEAD <file>` puts back the committed file, and your staged edits then survive only in the index. nix#79 logs the #509 session losing review edits to `git restore -s HEAD`, and the #615 session had to re-apply a comment edit after a `git checkout --`. Commit before each mutation check. A WIP commit you amend later works. Parallel reviewers in one checkout undo each other's mutations (nix#79, the cinder#884 thread). So a reviewer that can write runs its mutation check in a worktree of its own, outside `/tmp`, which is a small tmpfs on the dev host. It creates one with `git worktree add --detach <dir> <reviewed SHA>`, sets it up as « Worktrees run through the dev shell » says, and removes it afterwards with `git worktree remove <dir>`. A read-only reviewer leaves the mutation check to the author.
- **A lint script that reads source states its reach in its header.** List each form it reads, each form it fails by name, and each form it does not see, as `scripts/lint-type-ramp.ts` does, and give each form it reads or fails by name a fixture. Draw the list from the platform's API, not only from what `src/` writes today: for a font size, a CSS property in any case and its shorthand, a `style` attribute or directive, an SVG attribute, a component prop, the DOM style API. A reviewer takes a form the header names as not seen as settled. On #365, review found missing forms one at a time: four rounds, 34 minutes.

## Writing unit and component tests

- **Route pages mount like components.** Import the page dynamically, after every `mock.module(...)` call: `const { default: Page } = await import('./+page.svelte');`. A static import hoists above the mocks. Mock `$app/state` (a `page.url` getter), `$app/navigation`, `$app/env` and `svelte-sonner` (its dist can't load under `bun test`: it fails with `Cannot find package 'runed'`), and cast a minimal `PageData` with `as unknown as PageData`. Model: `src/routes/child/[id]/log/log.hint.test.ts`.
- **An enhanced form's result: keep the `enhance` callback.** The usual `$app/forms` mock (`src/test/app-stubs.ts` and the per-file copies) makes `enhance` a no-op, so only e2e sees what a page or a ConfirmModal does with an applied result. To test a dialog's result here, use `captureEnhance()` from `src/test/enhanced-submit.ts` (models: `submitDelete` in `src/routes/account/passkeys/page.svelte.test.ts`, `submitDialog` in `src/routes/child/[id]/settings/page.svelte.test.ts`):
  1. Before the dynamic page import, `const forms = captureEnhance(); mock.module('$app/forms', () => forms.module());`.
  2. `await forms.submit(open, result, update)`. `open` is the click that mounts the dialog's form: a ConfirmModal's form mounts only once its opener is clicked. The helper submits the last form that registered during `open`, so a page form that registered at mount is never the one submitted, and it throws when none did. `update` re-renders the page's `form` prop and stands in for SvelteKit; `trackSubmission` and ConfirmModal run for real. The helper awaits `tick()` before it returns.
- **A repas form's result: mock the durable submit.** The log and edit pages post through `RepasForm`, which sends the form with `submitRepas` (`src/lib/offline/submit.ts`) instead of `enhance`, and the `$app/forms` stub's `applyAction` does nothing, so the page's `form` prop never changes. To test what an edit page does with an answer (model: `src/routes/child/[id]/log/[entryId]/entry-edit.test.ts`):
  1. Before the dynamic page import, mock the submit to return a mutable answer: `mock.module('#lib/offline/submit.js', () => ({ submitRepas: async () => ({ kind: 'sent', result: answer }) }))`.
  2. Set `answer` to the `ActionResult`, then `fireEvent.submit` the form. The page receives it through RepasForm's `onapplied`.
  3. `waitFor` the change: the submit settles a few microtasks later.
- **Label tests: assert on `label.control`.** happy-dom pairs a field with every `label[for]` that names its `id`, so `getByLabelText` still finds a dialog's field when another field on the page has the same `id`. A browser points the label at the first field with that `id` in the page, and the dialog's field has no name (#468). `label.control` returns a single element for the `id`, so the assertion fails on the duplicate.
- **Server-rendered markup: prove it in e2e.** `svelte-loader.preload.ts` compiles every component with `generate: 'client'`, so a component test sees what the client renders and never the HTML the server sends. A Playwright test with JavaScript off (`openWithoutJavaScript` from `e2e/_helpers.ts`) sees only that HTML (model: `a refused login moves focus to the alert…` in `e2e/auth.spec.ts`). A component test can still stand in for the hydration render. `isHydrated()` from `#lib/hydration.js` returns false until a test calls `markHydrated()`, just as it returns false while the client hydrates. A test that calls `markHydrated()` calls `resetHydration()` from the same module in `afterEach`, because the `afterEach` in `bunfig.preload.ts` empties only `document.body` (model: the `FormError focus` tests in `src/lib/components/ui/FormError.test.ts`, #469). Call it in `beforeEach` instead when a test stubs `document`: the preload puts `document` back only after the file's own `afterEach` has run (model: `src/lib/hydration.test.ts`).
- **Focus checks: assert `document.activeElement`.** happy-dom sets no `autofocus` attribute on a `div` when Svelte sets the property, so assert where focus went, after `await tick()`. Svelte's autofocus moves focus only while the body has it, so a test asserting that an element leaves focus alone first puts focus on the body and asserts it. Compare `document.activeElement?.tagName` with `'BODY'`, because a failing `toBe(document.body)` prints happy-dom's whole window object.
- **An element that must be absent: assert `el?.outerHTML ?? null`.** A failing `toBeNull()` on a happy-dom node prints the whole window object too, thousands of lines with no markup in sight. Asserting the markup prints the element that should not be there (model: `src/routes/content-page-headings.svelte.test.ts`).
- **Time-zone logic: pin `process.env.TZ`.** The dev host runs Paris time, so a host-local-time bug passes locally and fails only on a UTC server (#451). Set `process.env.TZ` in `beforeEach` (bun honours the change at run time) and restore it in `afterEach`, with `delete` when it was undefined: `pinHostZone(zone)` from `src/test/bun-test-utils.ts` does both for the describe block it is called in. `describe.each` over zones runs every case once per host zone. Models: `src/lib/utils/dates.test.ts`, `src/routes/child/[id]/paris-midnight.test.ts`. Day logic lives in `src/lib/utils/civil-calendar.ts`; read its header.
- **Password hashes are cheap under `bun test`.** `bunfig.preload.ts` sets `__TEST_RELAXED_ARGON__`, so while `NODE_ENV` is `test`, `hashPassword` uses the E2E cost (`m=4096,t=1`) instead of the production `m=19456,t=2`. bun test sets `NODE_ENV=test` unless your shell already exports another value, which silently brings back the full cost. `Bun.password.verify` reads the cost from the stored hash, so verifying against those hashes is cheap too. The login decoy hash is built once per process, by the first unknown-address login, at the cost in force at that moment. Every Vite build inlines `false`. A test that needs the production cost stubs the global with `stubGlobal('__TEST_RELAXED_ARGON__', false)` from `src/test/bun-test-utils.ts`, and the preload's `afterEach` restores it. Model: the `hashPassword cost` block in `src/lib/server/auth.test.ts`.
- **An unhandled rejection fails the running test.** `bun test` fails whichever test is running when a promise rejection goes unhandled, even with a `process.on('unhandledRejection')` listener and even when the test body ends synchronously. A regression test for an "unhandled rejection" Sentry issue only has to drive the code path, with no listener or sleep.
- **A promise that can stay pending: `await p.catch((e: unknown) => e)`, then assert.** On bun 1.4.2 and 1.4.4 (checked 2026-10-27), `expect(p).rejects` and `expect(p).resolves` wait for `p` without letting the 5 s test timeout fire, so when `p` never settles the file spins at full CPU and never ends. A promise stays pending that way when an earlier failing test leaves module state stuck, such as the offline queue's `inFlight` (#452). Model: the `rejects and frees the lock when its pass throws` test in `src/lib/offline/queue.test.ts`.

- **A wall-clock assertion: assert the limit the code hands its tools, not the time a run took.** CI's unit-test job shares the runner with other repos' jobs, and a loaded runner stalls a process for seconds: in #582's CI run, `fails a 500 at once, without a retry` took 3.7 s where it usually takes 150 ms (#572). Bash's start-up and the work after a run's last request fall outside any deadline the script keeps, so an upper bound of the deadline plus a slack fails sooner or later. `scripts/smoke-prod.test.ts` raised its slack from 500 ms to 2 s after run 346 overshot by 887 ms, and run 354 still overshot by 2.7 s (#575); #593 retired it. These rules replaced it:
  1. To prove that a run ends by a deadline, read the limit the script hands its tools. The `logCurl` option puts a curl first on PATH that logs each call's arguments to `run.curls`, then execs the real one. Each request's `--max-time` is above 0 and at most the time from the start to the deadline that request must end by: the wait's end for a `/_app/version.json` poll, the run deadline for a check. The fake `sleep` logs its delays to `run.sleeps`: `run.sleeps[0]` holds the timer's delay before its TERM, and `run.sleeps.at(-1)` the wait's pause before its last poll.
  2. Keep a wall-clock upper bound only to tell a run that ends near its deadline from one that waits out something much longer, curl's own 20 s or a stalled upload-pack. Put it at least 5 s above the deadline and at least 5 s below that wait, and the test's timeout above that wait, so a missed deadline fails on the bound. A lower bound holds under any stall, which only makes a run longer, when it counts from a clock read taken before the code under test starts its timer. A read taken after that start misses any stall in between: the offline queue's deadline tests read the clock in their fake transport, after the replay's timer started, and run 510 measured 46 ms against the 49 ms bound of a 50 ms deadline (#685).
  3. Give every step that must come before a deadline at least 6 s after the script starts. A larger `SMOKE_WAIT` or `SMOKE_CHECK_TIME` costs nothing where the run ends early (a Ctrl-C) or the test reads a value from a fake instead of waiting for it. A run that must last until a real deadline gets longer: #593 took the file from 25 s to 45 s.
  4. Where a KILL comes within seconds of a TERM, assert nothing that needs a process to run between the two, such as a file that a TERM trap writes. Assert what holds once the KILL has come, such as the process gone. A KILL that follows the TERM at once can land before the trap runs (#581). 1 s was not enough either: in `main` run 565, on a loaded runner, the stalled upload-pack's trap file was still empty after a KILL that came at least 1 s after the TERM (#712). The `keeps $TMP` and `prints no bash warning` tests need the fetch's child to run its trap first, so their fake sleep puts the KILL 20 s after the TERM (#726).

  Before you push such a test, run its file under two busy loops per core: `bash -c 'for i in $(seq $(( $(nproc) * 2 ))); do (while :; do :; done) & done; nix develop -c bun run test scripts/smoke-prod.test.ts; rc=$?; kill $(jobs -p); exit $rc'`. That run does not reproduce the runner's stalls, and two of #574's tests passed it before failing on `main` (#581). Run the file under two stalls too, after one `bun run test`, which generates the files the test preloads import. A stall of bash's start-up, before the script's first clock read, reaches every test. #572's `curl` shim, which stalls the script after its first `/_app/version.json` request, misses the tests that use `logCurl`, whose curl runs the real one by its absolute path. A stall before the first fetch of origin tests the 6 s windows of rule 3. Take `sleep` and `git` from the dev shell, since the tests put a fake `sleep` first on PATH:

  ```sh
  D=/tmp/smoke-stall; mkdir -p "$D/gitbin"
  S=$(nix develop -c bash -c 'command -v sleep')
  G=$(nix develop -c bash -c 'command -v git')
  # Bash reads BASH_ENV before the script: 3 s before its first clock read.
  printf 'case "$0" in *smoke-prod.sh) [ -n "${STALLED:-}" ] || { export STALLED=1; %s 3; } ;; esac\n' "$S" >"$D/startup.sh"
  # The ls-files check runs after that read, before the first fetch and poll.
  printf '#!/bin/sh\ncase " $* " in *" ls-files "*) %s 4.5 ;; esac\nexec %s "$@"\n' "$S" "$G" >"$D/gitbin/git"
  chmod +x "$D/gitbin/git"
  nix develop -c env BASH_ENV="$D/startup.sh" bun --conditions=browser test --timeout=20000 scripts/smoke-prod.test.ts
  nix develop -c bash -c "PATH=$D/gitbin:\$PATH bun --conditions=browser test --timeout=20000 scripts/smoke-prod.test.ts"
  ```

  Keep `\$PATH` escaped inside `bash -c`: the outer shell would expand it before the dev shell sets PATH, and bun would not be found (exit 127).

## Writing E2E tests (Playwright)

- **An absent toast or a single message: take one count.** `toHaveCount(0)` retries for 5 s and svelte-sonner toasts expire after 4 s, so it waits a wrong toast out and passes (#437). Wait for the triggering work to finish (e.g. `expect.poll` on the queue), then assert `expect(await locator.count()).toBe(0)`, or `.toBe(1)` for a message that must show once. Watch the check go red before trusting it: against the old code, or, when the old code never shows the message, against a temporary mutation that shows it twice (a `toast()` next to the inline message). Models: the queue-replay test in `e2e/offline.spec.ts`, the counts in `e2e/account.spec.ts`.
- **Keep a user's JavaScript steps on the `page` fixture.** A context from `browser.newContext()` starts cold: it fetches every chunk again and installs the service worker, which precaches the whole app. In #501's first CI run, the `a refused save with JavaScript` tests, which each opened one, took 17 s to over 30 s, while the older `edit.spec.ts` tests on `page` took 9 s. That cost outweighs a branch on a `javaScript` flag in a parametrized test. Open a second context for the same user only to turn JavaScript off, with `openWithoutJavaScript` from `e2e/_helpers.ts`. A second user still needs a context of their own.
- **Budget a new test by its time in a busy CI run.** #501's edit tests took 2 s locally, 3 to 5 s on an idle CI runner, and 9 to 29 s when other jobs shared the runner. ## Reproducing a bug on a production build

Dev mode registers no service worker and serves unbundled modules instead of the `/_app/immutable/` chunks, so chunk-load and service-worker failures show only on a production build. Reproduce them there, and rebuild and restart after every code change (a build takes about 30 s):

```sh
nix develop -c env ORIGIN=http://localhost:5722 bun run build
nix develop -c env DATABASE_PATH=repro.db PORT=5722 WEBAUTHN_RP_ID=localhost NODE_ENV=production bun build/index.js > repro.log 2>&1 & echo $! > repro.pid
```

5722 is the port for #722. Take 5000 plus your issue number, so that it differs from the port « E2E from a worktree: give the run a free port » gives the E2E run of the same worktree, check first that `ss -ltn 'sport = :<port>'` shows no listener, and give `ORIGIN` the same port. A server that finds its port taken exits, and its `repro.pid` then names no process. The three files sit in the worktree, where git ignores them. Stop the server with `kill "$(cat repro.pid)"`, then check with the same `ss` call that the port is free: `nix develop -c` execs bun, so that PID is the server's own. A kill by name or by port also stops other worktrees' servers, E2E runs included. The repo's rule hook blocks `pkill`, `killall`, `fuser -k` and a command that holds both `pgrep` and `kill` (`.claude/rule-hook/rules/block-kill-by-name.md`).

The browser Sentry SDK and the `/monitoring` tunnel start only when `PUBLIC_SENTRY_DSN` is set. It is read at run time, so for a browser Sentry repro add a fake one to the `bun build/index.js` line (for example `PUBLIC_SENTRY_DSN=https://0123456789abcdef0123456789abcdef@o1.ingest.de.sentry.io/2`), with `PUBLIC_SENTRY_TRACES_SAMPLE_RATE=0` and `PUBLIC_SENTRY_REPLAYS_ON_ERROR_SAMPLE_RATE=0` to keep traces and replays out of the envelopes. Leave `SENTRY_DSN` unset, and intercept `/monitoring` in the browser to read the envelopes: the tunnel would otherwise relay them to the DSN's host. Delete `repro.db*`, `repro.log` and `repro.pid` afterwards.
