# Deploy & migration runbook

Operational checklist for releasing Diversif. Background (stack, backups, legal
env vars, reverse-proxy headers) lives in [`README.md`](./README.md); this file
is the **"did I actually run it?"** procedure so nothing is left to memory.

The reference deploy is **Coolify + Railpack**, a single `oven/bun` container
with the SQLite file on a persistent volume at `/app/data`. Migrations and the
food-catalog seed run **automatically on every container start** and are
idempotent (`src/lib/server/db/index.ts` → `migrate()` + `seedFoods()`).

---

## 1. Before any deploy that includes a migration

A migration ships whenever `drizzle/` has a new `NNNN_*.sql` file (generated by
`bun run db:generate` after a `schema.ts` change).

1. **Take a backup and verify it restores.** A backup you have never restored is
   not a backup.

   ```bash
   # On the host, against the live volume:
   sqlite3 "$DATABASE_PATH" "VACUUM INTO '/app/data/backups/pre-deploy-$(date +%F-%H%M).db'"

   # Prove the snapshot is restorable (integrity + foreign keys + row counts):
   DATABASE_PATH=/app/data/backups/pre-deploy-YYYY-MM-DD-HHMM.db bun run db:verify-backup
   # exits non-zero if the file is corrupt, truncated, or missing critical tables
   ```

   `bun run db:verify-backup` with **no** argument instead snapshots the live
   `DATABASE_PATH` and verifies that — use it to spot-check the backup _method_.

2. **Dry-run the migration on a copy of prod data**, never just an empty dev DB.
   Migrations that are clean on an empty schema can still fail on real rows
   (NOT NULL adds, FK tightening, unique backfills):

   ```bash
   cp /app/data/diversif.db /tmp/migration-dryrun.db
   DATABASE_PATH=/tmp/migration-dryrun.db bun -e '
     import { Database } from "bun:sqlite";
     import { drizzle } from "drizzle-orm/bun-sqlite";
     import { migrate } from "drizzle-orm/bun-sqlite/migrator";
     const db = new Database(process.env.DATABASE_PATH);
     db.exec("PRAGMA foreign_keys = ON;");
     migrate(drizzle(db), { migrationsFolder: "./drizzle" });
     console.log("dry-run migration OK");
   '
   DATABASE_PATH=/tmp/migration-dryrun.db bun run db:verify-backup   # post-migration integrity
   rm -f /tmp/migration-dryrun.db*
   ```

3. **Write a rollback note** for any _destructive_ migration (drop/rename column,
   data-rewriting UPDATE). Put it as a comment at the top of the `.sql` file:
   what it changes and how to revert (almost always: _restore the pre-deploy
   backup and redeploy the previous image tag_ — SQLite has no down-migrations
   here). Additive migrations (new nullable column, new index, backfill) need no
   rollback note beyond the backup.

## 2. Deploy

1. Push to the branch Coolify watches (or trigger the deploy).
2. The container restarts; `migrate()` runs the pending `drizzle/*.sql` files in
   order, then `seedFoods()` reconciles the catalog. Both are idempotent, so a
   re-deploy of the same image is a safe no-op.
3. **Verify migration success** before considering the deploy done:
   - Container logs show no `subsystem: db-migrate` error (failures are captured
     to Sentry with that tag and re-thrown, so a bad migration crashes boot
     rather than serving a half-migrated DB).
   - Load `/login` and one authenticated page; check Sentry for new 5xx.

## 3. Rollback

If a migration corrupts data or boot fails:

1. Stop the container.
2. Restore the pre-deploy backup over `/app/data/diversif.db` (and remove stale
   `-wal` / `-shm` sidecars).
3. Redeploy the **previous** image tag (so its code matches the restored schema).
4. Run `bun run db:verify-backup <restored-file>` to confirm the restore is sound.

## Pre-launch environment gate

These are **not** code — they are deployment config that silently degrades
security or legal pages if unset. Confirm each in the Coolify environment before
exposing the instance to anyone outside the maintainers.

| Variable                                                                                                          | Why it matters if missing                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NODE_ENV=production`                                                                                             | Session cookie `Secure` flag and the HSTS header are **only** emitted in production (`auth.ts`, `hooks.server.ts`). Unset → cookies sent over plain HTTP, no HSTS.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `DATABASE_PATH=/app/data/diversif.db`                                                                             | Must point at the persistent volume, or data is lost on redeploy.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `WEBAUTHN_RP_ID`                                                                                                  | Must equal the bare registrable host (e.g. `diversif.app`), or passkeys reject every origin.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `LEGAL_CONTROLLER_NAME` / `_EMAIL` / `_ADDRESS`, `LEGAL_PUBLICATION_DIRECTOR`, `LEGAL_HOST_PROVIDER` / `_ADDRESS` | Legal pages render « à compléter » until set — see README.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `ADDRESS_HEADER` / `PROTOCOL_HEADER` / `HOST_HEADER`                                                              | Behind a proxy, without `ADDRESS_HEADER` the per-IP rate limits see the proxy as one client and one bad actor can lock everyone out — see README "Reverse proxy". The image deliberately bakes **no** default: adapter-node throws on requests lacking the configured header (a baked `x-forwarded-for` would take down any deploy without a proxy), and client-supplied `x-forwarded-for` is spoofable. Set `ADDRESS_HEADER=cf-connecting-ip` behind a Cloudflare Tunnel; `ADDRESS_HEADER=x-forwarded-for` + `XFF_DEPTH=<trusted proxies>` behind a directly-exposed proxy; leave it unset only when clients hit the container **directly** (socket address is then correct). The server logs a `[diversif:boot]` warning when `PROTOCOL_HEADER` is set without `ADDRESS_HEADER`. |
| `SENTRY_DSN` (+ `SENTRY_ENVIRONMENT`, `SENTRY_RELEASE`)                                                           | Errors in the wild reach you instead of dying silently.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |

### Launch ops backlog (deferred from [`TOOLING_AUDIT.md`](./TOOLING_AUDIT.md))

Two deployment-side items are **not yet done** and must be closed before opening
the instance to other families. They are infra/config, not code, so they live
here rather than in the repo — and intentionally **not** in `PARKING_LOT.md`,
which is for maybe-never work; these are required.

- [ ] **B1 — Off-box, continuous backups.** Today the only off-box copy is the
      manual pre-deploy `VACUUM INTO` snapshot above; the recurring cron is
      unscheduled. For a single-file SQLite DB holding other families' data,
      adopt **Litestream** streaming replication to an S3-compatible target
      (e.g. Cloudflare R2): it gives point-in-time recovery (seconds of RPO vs.
      up to 24 h for daily snapshots), needs no app changes, and its
      prerequisite — WAL mode — is **already enabled**
      (`src/lib/server/db/index.ts`). Keep the pre-deploy `VACUUM INTO` snapshot
      as the belt-and-braces pre-migration copy, and periodically run
      `bun run db:verify-backup` against a pulled-back replica so the restore
      path is exercised, not assumed.
- [ ] **O1 — Self-hosted error monitoring (optional, data-sovereignty).** The app
      already ships the Sentry SDK (`@sentry/sveltekit`); **GlitchTip** is
      Sentry-SDK wire-compatible, so adopting it is a config swap, not a code
      change: point `SENTRY_DSN` / `PUBLIC_SENTRY_DSN` at a self-hosted GlitchTip
      instance and **add its ingest origin to the CSP `connect-src`** in
      `svelte.config.js` (which currently allow-lists `*.ingest.*.sentry.io`).
      No hook/SDK changes needed. GlitchTip omits some Sentry features (Seer/AI,
      certain performance views) but covers error capture.

**Pre-migration backups carry raw session tokens.** Sessions are now stored as
sha256 digests at rest, but any backup taken **before** the session-hashing
deploy contains raw bearer tokens that remain valid for up to 30 days from
their creation. Treat those snapshots as credential-bearing material — same
handling as a secrets file — until they age out of the backup retention window.

### Signup & abuse controls

Signup is **open by decision** — anyone can register. The exposure is bounded by:

- **`INVITE_ONLY`** (optional, default open): set `INVITE_ONLY=true` to require a
  valid, unexpired invite code for every new account. A dormant lever — flip it
  if open signup is abused, no code change needed. Anything other than the exact
  string `true` keeps signup open.
- **Per-account creation caps** (code, not config): child creation is limited to
  10/hour per account, and each child may have at most 10 simultaneously-active
  (unused, unexpired) invites. Both are generous headroom for any real parent;
  they only stop an account from spraying unbounded rows. Tune in
  `child/new/+page.server.ts` (`CHILD_CREATE_LIMIT`) and
  `child/[id]/settings/+page.server.ts` (`MAX_ACTIVE_INVITES_PER_CHILD`).
- **Email verification is deferred** — there is no mail sender (see
  `PARKING_LOT.md`). Email is collected as the login identifier but not verified.

## Concurrency decision (lost updates)

Co-parent edits to shared records (`children`, `food_entries`) are deliberately
**last-write-wins**: two co-parents almost never edit the same row in the same
second, so optimistic-locking UX is not worth its complexity for v1. Both tables
carry an `updated_at` column (set on every write, backfilled from `created_at`)
so an edit is auditable and optimistic locking can be layered on later **without
another schema migration** if real usage ever shows concurrent clobbering. See
the comment on `children.updatedAt` in `src/lib/server/db/schema.ts`.
